# 모바일 앱 — "사진만 찍어두면 알아서 기록" (아이디에이션)

> 상태: 🟡 아이디에이션 — 구현 결정 전. 2026.09.19 작성.
> 관련: `docs/features/books.md`(현재 등록 흐름), `components/books/BarcodeScanner.tsx`
> (이미 있는 `@zxing/browser` 스캐너), `docs/api.md`(SEOJI 도서 검색)

---

## 0. 역할 분담을 먼저 못 박는다

| | 웹 | 앱 |
|---|---|---|
| 성격 | **보여주는 창** | **쌓는 도구** |
| 핵심 화면 | 지형도(감상·공유) | 카메라 |
| 사용 시점 | 가끔, 앉아서 | 매일, 책 덮기 직전 |
| 성공 지표 | 공유·재방문 | **기록 누락률** |

앱이 이겨야 하는 경쟁자는 다른 독서 기록 앱이 아니라 **"그냥 아무것도 기록 안 하기"**다.
그래서 앱의 목표는 기능을 많이 담는 게 아니라 **책 덮기 직전 5초를 가져오는 것** 하나다.

---

## 1. 목표 인터랙션

> 앱을 연다 → 이미 카메라다 → 셔터 → 끝.

확인 화면도, 어느 책인지 고르는 단계도, "저장되었습니다" 토스트도 기본 경로에는 없다.
**사용자를 붙잡는 모든 단계가 기록의 적이다.**

이게 되려면 사진 한 장에서 두 가지를 알아내야 한다: ① 어느 책인가 ② 몇 쪽인가.

---

## 2. 두 가지 촬영 모드

### A. 책 등록 — 표지/바코드 한 장

이미 웹에 `@zxing/browser` 바코드 스캐너가 있다. 앱에서는 카메라를 열자마자 프레임 안에
ISBN 바코드가 들어오면 **셔터 없이** 자동 인식 → SEOJI 검색 → 등록. 사용자는 책 뒤표지를
비추기만 한다.

- 바코드가 없거나 안 읽히면(도서관 필름 커버, 절판 구간, 해외 도서) **표지 OCR → 제목 검색**
  폴백. 이 경우에만 후보 목록을 보여준다.

### B. 진도 업데이트 — 펼친 페이지 한 장  ← **여기가 핵심**

펼친 책을 위에서 한 장 찍으면 **쪽번호를 읽어서** `current_page`를 갱신한다.

**왜 이게 현실적으로 가능한가**

- 쪽번호는 본문 여백에 **고립된 짧은 숫자**로 인쇄된다. 문장 속 숫자와 달리 주변이 비어
  있어서 위치(상단/하단, 안쪽/바깥쪽 여백)만으로 후보를 크게 좁힐 수 있다.
- 펼침면이면 숫자가 둘 잡힌다 → **큰 쪽**을 택한다(거기까지 읽었으므로).
- 직전 `current_page`가 있으므로 **"이전 값보다 크고, `total_pages` 이하"**라는 강한 제약을
  걸 수 있다. OCR이 `123`을 `723`으로 잘못 읽어도 대부분 이 제약에서 걸러진다.

**어느 책인지는 물어보지 않고 추론한다**

1. '읽는 중' 책이 **1권이면** → 그 책. 질문 없음. (대부분의 사용자가 여기 해당)
2. 여러 권이면 → ① 찍힌 쪽번호가 각 책의 `total_pages` 범위 안인가 ②
   `status_changed_at`이 가장 최근인 책 우선, 으로 후보를 줄인다.
3. 그래도 애매하면 **후보 2~3권만** 큰 표지 버튼으로. 목록 스크롤은 안 된다.
4. 보너스: 많은 책이 페이지 상단에 **러닝 헤드**(책 제목 또는 장 제목)를 인쇄한다.
   이게 찍히면 제목 매칭으로 1번 수준의 확신을 얻을 수 있다.

## 3. 실패해도 흐름이 끊기지 않는 설계 (가장 중요한 원칙)

OCR은 반드시 가끔 틀린다. 그래서 **정확도보다 실패 처리 설계가 중요하다.**

- 인식에 실패해도 **사진은 일단 저장**하고 "미정리함"에 넣는다. 셔터를 누른 사용자의
  행동은 어떤 경우에도 헛되지 않는다.
- 확인은 **나중에 한꺼번에.** 앱을 다시 열었을 때 상단에 조용한 배너 하나 —
  *"정리 안 된 사진 3장"* → 탭하면 숫자 키패드로 후루룩 확인.
- **셔터 직후에는 절대 사용자를 붙잡지 않는다.** 틀린 값이 잠깐 들어가는 것보다 기록이
  아예 안 남는 게 훨씬 나쁘다. 되돌리기는 쉽고, 안 찍은 건 복구가 안 된다.

---

## 4. 앱을 "찾아서 열게" 만드는 것들 (소구점)

사진 기록만으로는 "편리한 도구"에 그친다. 아래가 습관을 만든다.

1. **홈 위젯 / 잠금화면**
   지금 오르는 산과 진행률이 위젯에 떠 있고, 탭하면 바로 카메라. 웹으로는 절대 못 하는
   것이고, "앱을 왜 깔아야 하는가"에 대한 가장 단순한 대답이다.

2. **찍은 사진이 그대로 등반 로그가 된다** ⭐
   진도 갱신용으로 찍은 페이지 사진들이 버려지지 않고 그 책의 기록으로 쌓인다. 완독하면
   그 사진들이 **등반 앨범**이 된다 — 내가 이 산을 어떻게 올랐는지의 시각적 기록.
   - 사진을 찍을 이유가 "귀찮은 입력"에서 "남는 것"으로 바뀐다.
   - 완독 시점의 보상이 커지고, 웹의 공유 캡처와 자연스럽게 이어진다.
   - **이 항목 하나가 기능 전체의 성격을 바꾼다.** 우선순위 높게 볼 것.

3. **밑줄 캡처 → 인용 저장**
   페이지 사진에서 밑줄·형광펜 부분만 잘라 텍스트로 저장(쪽번호 자동 첨부).
   메모 입력이 **타이핑에서 촬영으로** 바뀐다. 리텐션 훅으로는 아마 가장 강력하다.
   (웹의 기존 메모 말풍선 기능과 그대로 연결된다.)

4. **오프라인 우선**
   지하철·비행기·산장에서 찍어도 로컬 큐에 쌓였다가 연결되면 동기화. 네트워크 때문에
   기록이 실패하는 일은 없어야 한다.

5. **알림은 최대 한 개**
   *"요즘 ◯◯산에 안 오르셨네요"* 정도. 연속 기록(스트릭) 압박·잔소리 알림은 이 앱의
   톤(산책)과 맞지 않는다.

## 5. 기술 선택 — PWA 먼저, 그 다음 네이티브

| | PWA (홈 화면 추가) | Expo / React Native |
|---|---|---|
| 카메라 | ✅ `getUserMedia` (zxing 그대로 재사용) | ✅ |
| 온디바이스 OCR | △ 서버 왕복 또는 WASM | ✅ Vision / ML Kit |
| 홈 위젯·잠금화면 | ❌ | ✅ |
| 백그라운드 업로드 큐 | △ 제한적 | ✅ |
| 개발 비용 | **매우 낮음** (현 코드 재사용) | 중간 |
| 배포 | 즉시 | 스토어 심사 |

**권장 경로**

1. **PWA로 흐름부터 검증한다** (1~2주 규모). "펼친 페이지 찍기 → 쪽번호 인식 → 갱신"이
   실제로 본인 독서 습관에 붙는지를 먼저 본다. 여기서 안 쓰이면 네이티브로 만들어도 안 쓰인다.
2. 붙으면 **Expo로 이식**하면서 위젯·온디바이스 OCR·백그라운드 큐를 얹는다. Supabase JS
   SDK를 그대로 쓸 수 있어서 데이터 레이어는 재작업이 거의 없다(단, 웹의 Server Actions
   대신 REST/RPC 경로가 필요).

**OCR 처리 위치**: 쪽번호 숫자 인식은 온디바이스(iOS Vision / Android ML Kit)로 충분하고,
무료·오프라인·즉시라는 장점이 크다. 표지→도서 식별처럼 어려운 것만 서버 폴백.

## 6. 필요한 DB / 스토리지 변경 (개략)

```sql
reading_shots (
  id, user_id, book_id null,        -- 책이 아직 특정 안 됐을 수 있음
  image_path text,                  -- Supabase Storage
  detected_page int null,           -- OCR 추정값
  confirmed_page int null,          -- 사용자 확인값
  status text,                      -- pending | confirmed | failed
  created_at
)
```

- `books.current_page` 갱신은 `confirmed` 시점에만.
- Supabase Storage 버킷 하나 + 소유자 RLS.
- 사진이 쌓이므로 **용량 정책**을 처음부터 정해둘 것(해상도 축소 저장, 보관 기간,
  Premium 플랜과의 관계).

## 7. 하지 않을 것

- **처음부터 완벽한 OCR을 목표로 삼기** — 실패 허용 설계(3번)가 정확도보다 중요하다.
- **웹 지형도를 앱에 그대로 이식하기** — 앱은 입력, 웹은 감상. 앱의 지형도는 작게 보여주는
  정도면 된다. 두 화면이 똑같으면 앱을 따로 만든 이유가 없어진다.
- **연속 기록(스트릭) 압박** — 톤이 맞지 않는다.
